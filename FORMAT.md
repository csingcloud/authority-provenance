# Authority Provenance bundle v0.1.1 — field tables and test vectors

**Companion to `SPEC.md`.** License: CC BY 4.0 (`LICENSE-SPEC`).

This document gives the member-level detail of the version 0.1 record (format
`cerydora-proof-bundle`, format version 1, payload schema 1) and the test
vectors for its serialization, seal and signature. `SPEC.md` is normative for
the envelope (§5.1), the value rules (§5.3), canonical serialization (§5.4),
the seal and signature (§5.5), versioning (§5.6) and verification (§7). Where
this document and `SPEC.md` differ, `SPEC.md` governs; report the difference
as an issue. Identifiers beginning `cerydora-` are historical (`SPEC.md` §2).

Verifiers validate the members below and treat everything else as data to be
digested. They MUST NOT reject a payload for carrying additional members:
payload growth is additive (`SPEC.md` §5.6).

The seal does not decide what a bundle discloses; curation does. Sealing an
`internal`-view bundle produces a portable record that may contain the
substance of open findings, and the format offers no protection against its
onward disclosure. The seal only makes whatever was built tamper-evident.

## 1. Payload members

### 1.1 Top-level payload members (payload schema 1)

Every member below MUST be present, with `null` only where the type column
permits it (`SPEC.md` §5.3: explicit null, never omission). This is checked
at `SPEC.md` §7.2 step 5 (`PAYLOAD_SCHEMA_VIOLATION`); otherwise a
load-bearing member such as `synthetic` could be omitted and the record would
still verify.

| Member | Type | Description |
|---|---|---|
| `payload_schema` | integer | MUST be `1` for this payload schema. |
| `bundle_id` | string | Unique bundle identifier, generated by the issuer (never chosen by a caller). |
| `view` | string | `"examiner"` or `"internal"`. |
| `generated_at` | string | Timestamp (`SPEC.md` §5.3). When the bundle was generated. Issuer-asserted (`SPEC.md` §7.4). |
| `synthetic` | boolean | True when built from synthetic fixture data. Carried inside the seal so a synthetic bundle can never be passed off as production evidence. |
| `authorization_source` | object | Identity of the canonical Authorization (§1.2). |
| `authorization_snapshot` | object | Deterministic examiner-safe projection of that Authorization (§1.3). |
| `authorization_snapshot_digest` | object | Qualified digest of the canonical snapshot (§1.4). |
| `evidence_manifest` | object | Citation-only evidence manifest (§1.5). |
| `cycle_id` | string | The reconciliation cycle the bundle packages. |
| `as_of` | string | Timestamp (`SPEC.md` §5.3). The cycle's as-of instant. |
| `attestations` | array of entry | Conformant claims (§1.6). |
| `remediation` | array of entry | Closed findings with sealed resolutions (§1.6). |
| `open_findings` | array of entry | Unresolved findings; empty in an examiner bundle unless policy discloses detail. |
| `working_state_summary` | object | String → integer counts of work in flight. |
| `coverage_gaps` | object | String → integer counts of unjudged matrix regions. Always travels with the bundle. |
| `complete_coverage` | boolean or null | Whether the cycle judged the full matrix. |
| `valid_until` | string or null | Timestamp (`SPEC.md` §5.3). Earliest evidence-staleness instant. |
| `policy` | object | The disclosure policy actually applied (§1.9). |
| `ledger` | object | Ledger integrity facts (§1.10). May be empty. |
| `disclosure` | object | Curation declaration (§1.11). May be empty. |

Array order in `attestations`, `remediation` and `open_findings` is
significant and preserved as produced. Canonicalization sorts object member
names only, never array elements.

### 1.2 Authorization source object

Identifies the canonical Authorization the bundle was evaluated against. The
canonical Authorization stays in the issuing organization's system of record;
it does not travel with the bundle.

```json
{
  "authorization_id": "<string>",
  "authorization_version": "<string>",
  "digest": {
    "algorithm": "sha256",
    "canonicalization": "cerydora-authorization-json-v1",
    "digest": "<64 lowercase hex characters>"
  }
}
```

`cerydora-authorization-json-v1` names the producer's
canonicalization of the Authorization document: SHA-256 over canonical JSON
with members sorted, no whitespace, and non-ASCII characters `\u`-escaped.
It is deliberately a different canonicalization from `SPEC.md` §5.4, and the
`canonicalization` label is what lets the two coexist. A verifier does not
recompute this digest, because the source document is not disclosed; it
checks the digest's syntax and the equality binding of `SPEC.md` §7.2 step 6.

### 1.3 Authorization snapshot (`examiner-core-v1`)

A deterministic, versioned projection of the canonical Authorization, safe to
give an examiner. Deterministic means that equal Authorization content,
`schema` and `profile` always yield byte-identical canonical snapshots.

```json
{
  "schema": 1,
  "profile": "examiner-core-v1",
  "source": { <exactly the §1.2 object> },
  "decision": {
    "status": "<lifecycle state>",
    "title": "<string>",
    "use_case": "<string>",
    "organization": "<string>",
    "decision_statement": "<string or null>",
    "role_disclaimer": "<string or null>"
  },
  "authority": {
    "role": "<string>",
    "organization": "<string>",
    "basis": ["<string>", ...]
  },
  "approver": {
    "role": "<string>",
    "identity_verified": <boolean>
  },
  "bounded_operation": {
    "statement": "<string>",
    "environment": "<string or null>",
    "regulated_data": ["<string>", ...],
    "in_scope": ["<string>", ...],
    "out_of_scope": ["<string>", ...],
    "autonomy_ceiling": "<string or null>"
  },
  "term": {
    "effective": "<YYYY-MM-DD>",
    "review": "<YYYY-MM-DD>",
    "expires": "<YYYY-MM-DD>",
    "reconciliation_cadence": "<string or null>"
  },
  "evidence_requirements": [
    {
      "claim_id": "<string>",
      "claim": "<string>",
      "source": "<string>",
      "freshness_sla_hours": <integer>,
      "failure_disposition": "<string>"
    }, ...
  ],
  "condition_roster": [
    {
      "condition_ref": "<opaque string>",
      "condition_type": "evidence_requirement" | "prohibited_flow"
                        | "activity_rule" | "exception",
      "summary": "<examiner-safe string>",
      "review_state": "evaluated" | "not_evaluated" | "withheld"
    }, ...
  ],
  "omitted_authorization_categories": ["<string>", ...]
}
```

Rules:

- **The roster is the applicable-condition set**, not the evaluated subset.
  Every condition of the Authorization that can be judged
  (evidence requirements, prohibited data flows, activity rules, exceptions)
  appears exactly once, ordered by `condition_ref` (UTF-8 byte order).
- `condition_ref` is an **opaque** string; recipients MUST NOT parse it. Its
  one guaranteed property is the join: every disclosed determination's
  `declared_state_ref` (§1.6) equals the `condition_ref` of exactly one roster
  entry (`SPEC.md` §7.2 step 7).
- `review_state` marks whether the packaged cycle evaluated the condition
  (`evaluated`), did not (`not_evaluated`), or evaluated it while the bundle
  withholds the result (`withheld`, for example an open finding whose
  substance the disclosure policy excludes).
- **A bundle that discloses a determination while withholding the condition
  semantics needed to understand it is nonconforming.**
- **Names are not carried.** The authority and approver blocks carry role and
  organization, never personal names. Approver identity detail (issuer,
  subject claim, time, method) does not travel. These and other ancillary
  categories are declared in `omitted_authorization_categories`, a
  deterministic, profile-fixed, sorted list. For `examiner-core-v1`:

  ```
  ["approver_identity_detail", "authority_name", "boundary_reasoning",
   "control_requirements", "data_flow_matrix_detail", "disposition_history",
   "evidence_predicates", "internal_notes", "relationships",
   "residual_risks"]
  ```

- `snapshot.source` MUST equal `authorization_source` exactly (`SPEC.md`
  §7.2 step 6).
- The field-level profile is provisional in version 0.1. Changes after
  publication follow `SPEC.md` §5.6.

### 1.4 Snapshot digest object

```json
{
  "algorithm": "sha256",
  "canonicalization": "cerydora-authorization-snapshot-v1",
  "digest": "<64 lowercase hex characters>"
}
```

`cerydora-authorization-snapshot-v1` is the `SPEC.md` §5.4 canonical
serialization applied to the `authorization_snapshot` object. Because the
snapshot is fully disclosed, a verifier MUST recompute this digest (`SPEC.md`
§7.2 step 6), unlike the source digest, which names an undisclosed document.

### 1.5 Evidence manifest (`citation-v1`)

Citation only: the manifest identifies **which evidence the issuer cited**,
with provenance and freshness. It makes no replay, completeness or
source-truth claim, and none may be inferred from it.

```json
{
  "schema": 1,
  "profile": "citation-v1",
  "entries": [
    {
      "evidence_id": "EVD-<16 lowercase hex characters>",
      "source": "<string>",
      "instrument": "<string or null>",
      "observed_at": "<timestamp or null>",
      "freshness_sla_hours": <integer or null>,
      "reference": {"kind": "<string>", "value": "<string>"} | null,
      "content_digest": {"algorithm": "sha256", "digest": "<64 lowercase hex characters>"} | null,
      "cited_by_claim_ids": ["<string>", ...]
    }, ...
  ]
}
```

Rules:

- `evidence_id` is **opaque and stable**: the same citation carries the same
  identifier in every bundle the issuer emits. Recipients and verifiers treat
  it as opaque; verifiers check uniqueness and ordering, never derivation.
- Entries are deduplicated and ordered by `evidence_id` (UTF-8 byte order).
- `reference` locates the evidence in the issuing organization's own systems
  (for example `{"kind": "customer-record", "value": "<their identifier>"}`).
  It is a pointer, not content.
- `content_digest` is `null` unless a named digest-disclosure policy permits
  it: evidence hashes can leak correlation or allow guessing of low-entropy
  facts, so disclosing a digest is itself a disclosure decision. Version 0.1
  defines no such policy; conforming producers emit `null`.
- When `content_digest` is non-null, its `digest` MUST be exactly 64
  lowercase hex characters; any other length, case or non-hex content is
  `PAYLOAD_SCHEMA_VIOLATION` (`SPEC.md` §7.2 step 5). The canonical spelling
  is the only conforming one.
- `cited_by_claim_ids` is sorted, and every member equals the `claim_id` of a
  disclosed entry (`SPEC.md` §7.2 step 7).

### 1.9 Policy object

The disclosure policy applied at curation time. All members boolean:
`include_resolved_findings`, `include_open_finding_detail`,
`include_open_finding_counts`, `include_open_finding_breakdown`,
`include_ledger_head_hash`, `include_ledger_record_count`,
`declare_curation`.

### 1.10 Ledger facts object

Either empty (`{}`) or carrying `verify` (string) and `chain_algorithm`
(string), plus, each only when the disclosure policy permits it,
`records_verified` (integer or null) and `head_hash` (string or null). Both
gated members are sensitive disclosures: the head hash is a cryptographic
commitment to a chain that also contains adverse records, and the record
count, across successive bundles, reveals the rate of the issuer's internal
record activity. The absence of either is a policy decision, not an error.

### 1.11 Disclosure object

Either empty (`{}`) or the curation declaration: `boundary`, `statement`,
`scope_of_withholding`, `policy_name`, `counsel_note` (strings) and `policy`
(object, §1.9 shape).

### 1.12 Optional members a verifier may read

Three payload members are not part of payload schema 1 and are not required
by it: `principal_results`, `execution_results` and `revalidation_results`.
Version 0.1 does not specify their contents. A bundle that carries none of
them conforms; no example in this package carries them.

A verifier MAY read each one and, when it is present as an array, report it
verbatim as an additive member (`SPEC.md` §5.6). A verifier MUST NOT require
them, MUST NOT treat their absence as an error, and MUST NOT let them change
any of the four results or the exit code (`SPEC.md` §7). The reference
verifier reports a member that is absent, or present but not an array, as
`not-included` in its text report and as `null` in its `--json` output. Like
every payload member, each is included in the digest.
